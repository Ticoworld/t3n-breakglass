# C-0 GitHub Security Archaeology

Research/retrieval date: 2026-09-01. Primary sources are official GitHub documentation.

## Relevant primitives

| GitHub primitive | What it proves | BreakGlass consequence |
|---|---|---|
| Deploy-key GET/DELETE | Deploy-key deletion is `DELETE /repos/{owner}/{repo}/keys/{key_id}`; successful delete is HTTP 204; not-found reads are 404. Deletion requires Administration write through an accepted fine-grained PAT or GitHub App installation token. | Current fixed target/GET verification is compatible, but 204 is only provider response evidence, not a T3N receipt. Source: [deploy keys REST](https://docs.github.com/en/rest/deploy-keys/deploy-keys?apiVersion=2026-03-10), retrieved 2026-09-01. |
| Deploy-key webhook | Official event documentation exposes a `deploy_key` event with documented `created` action and payload fields including key, repository, sender, and installation. A documented delete action was not found. | Do not build a proof that relies on a delete webhook. Detection of created/suspicious keys can be event-driven, but remediation outcome still needs GET/audit evidence. Source: [webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads), retrieved 2026-09-01. |
| Delivery ID | `X-GitHub-Delivery` is a GUID; redelivery keeps the same delivery ID. GitHub recommends deduplication using it. | Evidence ingress can reject duplicate deliveries before creating an incident. Current BreakGlass has no delivery ID field or ingress. Sources: [webhook headers](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks), retrieved 2026-09-01. |
| HMAC signature | GitHub signs raw request body with HMAC-SHA256; receiver must compare the `sha256=` signature in constant time before processing. | A gateway can verify authenticity, but current component has no event input or crypto/signing import. Source: [validating deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries), retrieved 2026-09-01. |
| Failed deliveries | GitHub does not automatically redeliver failed deliveries; manual/scheduled redelivery is required. | The evidence gateway must persist raw delivery and processing state; “GitHub will eventually retry” is not a liveness guarantee. Source: [failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries), retrieved 2026-09-01. |
| GitHub App JWT | App JWT uses RS256 with `iat`, `exp`, and `iss`; expiration must be no more than 10 minutes in the future. | A broker can mint installation tokens, but needs standing App private-key authority and a clock discipline. Source: [App JWT](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app), retrieved 2026-09-01. |
| Installation token | Installation access token expires after one hour and can be restricted to selected repositories and a subset of App permissions. | This is materially better than a standing PAT and is credible JIT provider privilege, though one hour is not one action and explicit revocation is still useful. Source: [installation auth](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps), [token generation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app), retrieved 2026-09-01. |
| Installation-token revocation | GitHub documents an endpoint to revoke an installation access token. | Broker can revoke after verified remediation; this is stronger than waiting one hour, but revocation is a separate provider call and must be recorded. Source: [revoke installation token](https://docs.github.com/en/rest/apps/installations#revoke-an-installation-access-token), retrieved 2026-09-01. |
| App private key | GitHub App private keys do not expire automatically and require manual revocation/rotation. | “No standing provider authority” is impossible with a conventional App alone. The private key must live in a separately protected broker/TEE and be rotated. Source: [managing App private keys](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps), retrieved 2026-09-01. |
| OIDC | GitHub Actions OIDC tokens represent workflow identity. They are not a general inbound webhook identity for an arbitrary T3N service. | OIDC can help a CI/workload broker, but cannot by itself authenticate a GitHub repository event arriving at BreakGlass. Source: [GitHub Actions OIDC](https://docs.github.com/en/actions/concepts/security/openid-connect), retrieved 2026-09-01. |
| Key identity/fingerprint | Deploy-key objects expose a numeric `id` and key metadata used by the REST endpoints. The reviewed deletion contract is keyed by numeric ID; a portable fingerprint field/conditional version is not a documented delete precondition. | Current authority uses numeric ID and exact GET; it should also store a canonical public-key digest where available, but cannot rely on provider fingerprint as a transaction fence. Source: [deploy keys REST](https://docs.github.com/en/rest/deploy-keys/deploy-keys?apiVersion=2026-03-10), retrieved 2026-09-01. |
| Audit/security logs | GitHub has audit-log/security surfaces, but the reviewed public deploy-key webhook/API docs do not establish a single portable, immediate delete-effect receipt for GitHub.com repositories. | A next design may correlate audit events when available, but exact GET remains necessary; do not claim universal audit closure. PROVEN IMPOSSIBLE / UNAVAILABLE as a current portable receipt. |
| Eventual consistency / races | Webhooks can fail and require manual/scheduled redelivery; deploy-key DELETE has no documented compare-and-swap or idempotency key. The live two-call test returned 204 for both calls. | Provider state must be verified and effect budget fenced before the call; GitHub cannot supply the full transaction. LIVE-EVIDENCE-PROVEN for observed race, PROVEN IMPOSSIBLE / UNAVAILABLE for provider-side atomic fence. |
| User tokens | GitHub user access tokens can be fine-grained/shorter-lived and revoked, but still represent user authority and are not an ideal emergency workload principal. | Prefer App installation tokens for exact repository permissions. |

## Feasibility answers

**No standing PAT:** yes. Replace the PAT with a GitHub App installation token minted only after an eligible incident. This does not remove standing authority: the App private key or an equivalent token broker remains.

**No manually typed target:** partially. A verified webhook payload carries repository and key metadata for creation events, but current GitHub documentation does not provide a universal deploy-key deletion event. Detection can derive the target; remediation must still re-fetch provider state.

**No invented incident:** only with a new ingress protocol. The gateway must verify raw HMAC, enforce event/action/schema, dedupe delivery ID, bind installation/repository, and commit the evidence digest before authority issuance. Current BreakGlass lets the operator write the incident directly.

**No destructive privilege before evidence:** feasible as an architecture, not present now. The authority record should reference an immutable evidence digest and a policy decision; the agent should never be able to manufacture either.

**Provider token not outlive remediation:** improved but not absolute. Installation token expiry is one hour; explicit token revocation can shorten exposure. GitHub documents token expiry/scoping but does not make a provider DELETE transactionally coupled to T3N state.

**Independently verifiable receipt:** feasible only by combining T3N host activity/audit with GitHub request/delivery metadata and a digest/signature. Current application proof is not independent.

## GitHub-specific ceiling

GitHub’s strongest contribution is a credible provider-side JIT path and authenticated event metadata. Its limitations are equally important: no documented delete webhook, no provider idempotency/conditional delete guarantee for this endpoint in the reviewed docs, eventual delivery/redelivery complexity, and a non-expiring App private key. The next product must show these edges rather than hide them.
