# C1-R6B-R4A candidate architecture

## Scope and status

This document describes the local, unregistered 2.0.4 candidate prepared after
the R6B-R3 state-only failure. No T3N registration, delegation update, C1
invocation, GitHub request, or provider mutation was performed in R4A.

The prior R3 run is preserved as failure evidence. It proved that two separate
broker processes reached the barrier and both received `CLAIM_WON` with the
same generation-1 claim identity. It did not prove the internal Terminal 3
cause. The application-level gap is that the old claim identity was derived
only from incident and generation, so competing proposals were byte-identical.

## Candidate state and identity rules

The candidate keeps the existing private `winner-incidents` map and the same
fixed target fields. It adds two process-bound identities:

* `contender_nonce`: exactly 32 lowercase hexadecimal characters, generated by
  each broker process from 16 random bytes;
* `effect_start_id`: stored only after a broker-authorized `begin-effect`
  commits, and derived from a process-specific start nonce.

`claim-effect` now commits a provisional `PROPOSED` claim containing only the
claim ID and generation. The claim ID includes the contender nonce. It never
returns target details. `confirm-claim` is broker-only and read-only. It
returns `CONFIRMED` with committed target details only when the supplied claim
ID exactly matches the persisted claim; otherwise it returns `NOT_OWNER` or a
bounded denial without target details.

The state shape is:

```text
ACTIVE          attempts=0, no reservation/claim/start
RESERVED        attempts=0, reservation present, no claim/start
READY_RETRY     attempts=0, reservation present, generation advanced, no claim/start
EFFECT_CLAIMED  attempts=0, exact claim present, no effect start
EFFECT_STARTED  attempts=1, exact claim and effect start present
CLOSED          attempts=1, exact claim/start, VERIFIED_ABSENT
RECONCILE_REQUIRED / FAILED
                attempts=1, exact claim/start, bounded terminal classification
```

`valid_shape` rejects malformed state IDs, inconsistent generation/version
relationships, missing effect-start identity in consumed states, and any
attempt count above the one-effect budget.

## Effect-start boundary

The broker sequence is now:

```text
claim proposal
  -> confirm-claim
  -> validate committed target
  -> JIT provider authority and provider precheck
  -> begin-effect with process start nonce
  -> confirm-effect-start with exact persisted start identity
  -> provider DELETE
  -> provider reads and token revoke
  -> finalize-effect with exact claim + effect_start_id
```

`begin-effect` commits `EFFECT_STARTED`, sets `effect_attempts=1`, and stores
`effect_start_id`. `confirm-effect-start` is broker-only and read-only. The
provider DELETE is source-ordered after that confirmation. `finalize-effect`
does not increment the budget; it accepts only `EFFECT_STARTED` with the exact
claim and start identity. Recovery from `EFFECT_STARTED` uses reads and
reconciliation and cannot restore automatic destructive eligibility.

If a failure occurs before `begin-effect`, the broker may use
`release-not-attempted` only while its local control flow proves that begin was
never sent. After begin was sent, the claim is not released automatically.
An uncertain provider transport remains ambiguous and cannot trigger a blind
DELETE retry.

## Concurrency and stale contenders

The existing generation fence remains in force. A claim request carries the
expected stored generation. A successful proposal increments the stored
generation and binds the nonce. After release, the generation remains
advanced. A stale in-flight request carrying the old generation therefore
loses; an intentional fresh retry must explicitly use the newly observed
generation. Therefore the stale-after-release interleaving is
`CODE-IMPOSSIBLE_WITH_GENERATION_FENCE`; R4A retains and exercises this
pre-existing fence rather than claiming to have introduced it.

R4A local tests model both relevant cases:

1. conflict/retry: the first committed proposal changes state, so the stale
   retry loses;
2. double-affirmative application behavior: distinct proposals may exist in
   separate observations, but a single persisted authority can confirm only
   the exact identity it stores. The non-confirmed contender receives no
   target and cannot enter provider code.

The local two-process harness uses separate child processes, distinct nonces,
proposal persistence, a common proposal-completion barrier, and an atomic
single-owner confirmation step. It was run for 64 iterations.

## Evidence durability and replay

Each live broker child receives `C1_RESULT_FILE` and writes its sanitized
result atomically. The parent waits for both proposal result files before
allowing confirmation to continue, then reads the persisted final documents.
The documents contain claim/confirmation identity, provider-before/after
metadata, effect-start identity, token and DELETE counters, revocation and
finalization observations, but no credentials.

The live parent reads final operator state and requires `CLOSED`, one consumed
effect, and `VERIFIED_ABSENT` before it creates or launches replay. Replay is
therefore terminal-state-gated and cannot be used as proof against an
`EFFECT_CLAIMED` or `EFFECT_STARTED` authority.

## Claims not earned by R4A

This candidate is not registered and has no live state or provider evidence.
R4A does not prove Terminal 3 OCC behavior, provider-side exactly-once,
atomic T3N/GitHub transactionality, durable outbox support, zero standing
provider authority, webhook ingress, C1 pass, or submission readiness.

The GitHub App private key remains a standing trust root.
